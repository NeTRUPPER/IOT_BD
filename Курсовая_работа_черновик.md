## Введение

**Актуальность.** Системы интернета вещей (IoT) накапливают телеметрию, управляют устройствами и хранят учётные данные пользователей. Компрометация базы данных в такой системе ведёт к утечке показаний датчиков, несанкционированной отправке команд на оборудование и раскрытию персональных данных. Поэтому проектирование и внедрение встроенных средств защиты СУБД — обязательный этап разработки, а не опция.

**Цель работы** — продемонстрировать навыки использования встроенных механизмов защиты информации в СУБД PostgreSQL на примере базы данных `iot`, обслуживающей учёт пользователей, устройств, датчиков, команд и аудита.

**Задачи работы:**

1. описать предметную область и спроектировать модель разграничения доступа;
2. определить владельцев объектов, матрицу доступа и набор средств защиты;
3. реализовать аутентификацию, роли, ACL, RLS, шифрование и хэширование;
4. настроить журналирование и восстановление на момент времени (PITR);
5. проанализировать результаты и сформулировать выводы.

**Объект исследования** — реляционная база данных IoT-платформы.  
**Предмет исследования** — методы и средства защиты данных в PostgreSQL.

**Используемые инструменты PostgreSQL** (перечень для введения и заключения):

| № | Механизм | Назначение в работе |
|---|----------|---------------------|
| 1 | Аутентификация SCRAM-SHA-256, SSL/TLS | Проверка подлинности и защита канала |
| 2 | Роли и привилегии (GRANT/REVOKE) | Разграничение доступа на уровне объектов |
| 3 | Владельцы объектов (OWNER) | Разделение административных зон ответственности |
| 4 | Ограничения целостности (PK, FK, CHECK, UNIQUE) | Предотвращение некорректных данных |
| 5 | Row Level Security (RLS) | Доступ к строкам по владельцу/ACL устройства |
| 6 | SECURITY DEFINER-функции | Контролируемые операции (команды, API-ключи, сессия) |
| 7 | Расширение `pgcrypto` | Хэширование API-ключей, симметричное и асимметричное шифрование |
| 8 | Прикладной аудит (`audit.login_log`) | Журналирование входов |
| 9 | WAL-архивирование, шифрование архивов | Сохранность журнала изменений |
| 10 | `pg_basebackup`, PITR | Резервное копирование и восстановление на момент времени |
| 11 | Контрольные суммы страниц (`data_checksums`) | Обнаружение повреждений на носителе |

**Среда выполнения:** Docker Compose, образ `iot_postgres:16`, конфигурация в каталоге `db/`, инициализация — `db/init/001_schema.sql`, `002_seed.sql`.

**Описание предметной области.** Рассматривается информационная система учёта IoT-инфраструктуры предприятия (лаборатории, офисы, цеха, склад, серверные). Система хранит:

- **учётные записи** пользователей (`app.user_accounts`);
- **устройства** — шлюзы и контроллеры (`app.devices`);
- **матрицу доступа** пользователей к устройствам (`app.device_user_acl`);
- **датчики и показания** (`app.sensors`, `app.sensor_readings`);
- **команды** на устройства (`app.device_commands`);
- **секреты устройств** в зашифрованном виде (`app.device_secrets`);
- **API-ключи** (хранится только хэш) (`app.api_keys`);
- **справочники** типов датчиков и единиц измерения (`ref.*`);
- **буфер приёма** сырых данных (`stg.ingest_raw`);
- **журнал входов** (`audit.login_log`).

Пользователи работают через роли приложения; администраторы БД — через выделенные роли `ddl_admin`, `dml_admin`, `security_admin` и суперпользователя `iot_dba` (переименован с предустановленного `postgres`).

#### 1.1.3. Обобщённая роль администратора и предустановленный пользователь

**Задачи обобщённой роли администратора** в реализации БД `iot`:

| Функция | Исполнитель в проекте |
|---------|------------------------|
| Создание/изменение схем и таблиц | `iot_dba`, `ddl_admin` |
| Назначение владельцев и привилегий | `iot_dba`, `security_admin` |
| Настройка RLS и политик | `security_admin` (владелец), `iot_dba` |
| Резервное копирование, PITR | `iot_dba` |
| Просмотр журнала входов | `auditor` / `auditor_login` |
| Управление ролями LOGIN | `iot_dba` |

**Предустановленный пользователь** СУБД при `initdb` — роль `postgres`. В рамках проекта выполнено **переименование** (п. 2.3 требований КР): **да**, новое имя — **`iot_dba`**.

Обоснование: имя `postgres` предсказуемо и часто используется злоумышленниками при подборе учётных данных; переименование снижает поверхность атаки «по умолчанию». Прикладные подключения по-прежнему выполняются отдельными LOGIN-ролями (`nikita_login`, `slava_login` и др.), а не от суперпользователя.

Способы применения в проекте:

1. **Новый кластер (Docker):** `POSTGRES_USER=iot_dba` в `docker-compose.yml` — суперпользователь создаётся сразу с новым именем.
2. **Существующий кластер:** SQL-скрипт `db/scripts/rename_superuser_to_iot_dba.sql`:
   ```sql
   ALTER ROLE postgres RENAME TO iot_dba;
   ```
   После этого в `pg_hba.conf` заменяются записи `postgres` → `iot_dba`, выполняется `SELECT pg_reload_conf();`.

### 2.1. Метод аутентификации

**Файл конфигурации:** `db/conf/pg_hba.conf`  
**Файл параметров:** `db/conf/postgresql.conf`

Для удалённых подключений к БД `iot` задано:

```text
hostssl all all 127.0.0.1/32 scram-sha-256
hostssl all all 172.19.0.1/16 scram-sha-256
```

Метод **`scram-sha-256`** (не MD5): пароли ролей хранятся в `pg_authid` в формате SCRAM; при аутентификации по сети передаётся доказательство знания пароля без передачи самого пароля в открытом виде.

Параметр в `postgresql.conf`:

```text
password_encryption = scram-sha-256
ssl = on
ssl_cert_file = '/etc/postgresql/ssl/server.crt'
ssl_key_file = '/etc/postgresql/ssl/server.key'
```

**Проверка в psql:**

```sql
SHOW password_encryption;  -- scram-sha-256
SHOW ssl;                  -- on
SELECT ssl, version, cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid();
```

*[Рис. 4 — `SHOW password_encryption` и `pg_stat_ssl`]*

**Пояснения и замечания.**

| Аспект | Оценка |
|--------|--------|
| Достоинства SCRAM | Устойчивость к перехвату пароля по сравнению с MD5; рекомендация PostgreSQL |
| SSL | Защита трафика от прослушивания; обязательна для удалённых клиентов |
| Недостатки | Требуются сертификаты и настройка клиента (`sslmode=require`); локально для `iot_dba` в Docker допущен `trust` только с localhost для администрирования |
| Риски учебной среды | Пароли ролей и WAL заданы в переменных окружения; в промышленной среде — Vault/HSM |

### 2.2. Объекты БД

### 2.8. Резервное копирование и восстановление

Реализован сценарий **PITR** (Point-in-Time Recovery) с шифрованием архивов WAL.

#### Этапы

1. **Контрольные суммы:** `SHOW data_checksums;` → `on` (`POSTGRES_INITDB_ARGS: "--data-checksums"`).
2. **Базовый бэкап:**
   ```bash
   docker exec iot_postgres pg_basebackup -D /tmp/pg_backup -U iot_dba -Fp -Xs -P
   docker cp iot_postgres:/tmp/pg_backup/. ./db/backups/lab4-base/
   ```
3. **Контрольная точка:** таблица `public.important_data`, запись «Данные до аварии», фиксация `recovery_target_lsn` и времени, `pg_switch_wal()`.
4. **Инцидент:** `DROP TABLE`, повторное создание, запись «Данные после аварии».
5. **Восстановление:** остановка БД, развёртывание бэкапа в PGDATA, `recovery.signal`, в `postgresql.auto.conf`:
   ```text
   restore_command = '/usr/local/bin/restore_wal.sh %f %p'
   recovery_target_lsn = '<ваш LSN>'
   recovery_target_inclusive = on
   recovery_target_action = promote
   ```
6. **Проверка:** после старта — одна строка «Данные до аварии».

**Шифрование WAL:** `archive_wal.sh` — gzip + OpenSSL AES-256-CBC → файлы `db/archive/*.gz.enc`.

## Заключение

В курсовой работе спроектирована и реализована защита базы данных `iot` для IoT-предметной области на платформе PostgreSQL 16.

**Использованные инструменты и объём применения:**

| Инструмент | Объём использования |
|------------|---------------------|
| SCRAM-SHA-256 + SSL | Аутентификация всех сетевых подключений |
| Роли и ACL | 7 прикладных ролей, 4 LOGIN, матрица GRANT |
| Владельцы объектов | Выделен `security_admin` для чувствительных таблиц |
| Целостность | PK/FK/CHECK/UNIQUE на всех основных сущностях |
| RLS | 7 таблиц, 8+ политик, FORCE RLS |
| pgcrypto | API-ключи (SHA-256), шифрование email и location_desc |
| SECURITY DEFINER | Сессия, команды, ротация ключей |
| Аудит | `audit.login_log` |
| WAL + шифрование архивов | Непрерывное архивирование с AES-256-CBC |
| PITR | Полный цикл: бэкап — инцидент — восстановление по LSN |

Практическая часть подтвердила: пользователь `slava_login` не видит чужие устройства; аудитор читает только журнал входов; после логической «аварии» PITR возвращает состояние на контрольную точку. Недостатки учебной конфигурации (пароли в env, `trust` для локального `iot_dba`) в промышленной эксплуатации должны быть устранены переводом секретов в KMS и ужесточением `pg_hba.conf`.

**Направления развития:** pgAudit для DDL/DML, репликация standby, автоматизация ротации ключей в `app.keys`, мониторинг `pg_stat_archiver` и тестирование RPO/RTO.
